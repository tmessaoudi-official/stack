## From CLAUDE.md § Gotchas & Pitfalls

- **The android platforms and build-tools pins are a ROLLING WINDOW, not three independent pins** (row 41, 2026-09-12). `GLOBAL_STACK_ANDROID_API_LEVEL_1/2/3` and `GLOBAL_STACK_ANDROID_BUILD_TOOLS_VERSION_PREV_2/_PREV_1/<unsuffixed>` are three `androidsdk:` records each on the same identifier with `(offset:2)`, `(offset:1)` and none — env-update's `(offset:N)` flag, "the N-th newest DISTINCT stable version", stable channel only, part of the cache key (`androidsdk:ID:CHANNEL:offN` — without that all three slots resolve to the same value, silently). Developer ruling: the window always covers the three latest STABLE releases, fully AUTO, no `(manual)`. Four consequences. **(1)** The `androidsdk` fetcher (the `sdkmanager:` type until row 46 — upstream deprecated that CLI for `android sdk`, and a leftover `sdkmanager:` annotation is now refused at parse time instead of being SKIPped silently by dynamic dispatch) reads Google's `repository2-3.xml` over HTTP and needs no local binary — the old one shelled out to `sdkmanager` on `tools/`, resolved nothing with the stack down, and could not parse `platforms;android-<LEVEL>` at all (its regex wanted a digit after `;`), which is what the year-old `(lock:)` on the API levels was really covering. **(2)** Every window shift changes `GS_ANDROID_SDK_WANT`, so the next boot `rm -rf`s `ANDROID_HOME` and reinstalls the SDK (15+ min, GBs) — the accepted price. **(3)** A shift that crosses a major (37.2 → 38.0, 36.1.0 → 37.0.0) is `HOLD` under decide.sh rule 7 like every other record and needs `--force-hold` / `--force-auto` to apply — the window is AUTO within a major, not across one; nothing android-specific changed that policy. **Ruling 2026-09-12: rule 7 stays; on a major bump apply the six android records with `--force-hold --confirm="Confirm override"`** — a plain `--apply` then leaves slot 3 on HOLD while slots 1-2 advance (`37.1 / 37.2 / 37.2`, a duplicate `platforms;android-37.2` in `_pkgs`), so the window is only intact under `--force-hold`. **(4)** The window is gated on COMPANION AVAILABILITY, and the class that actually bites is **channel skew, not a tag rename** (row 43, 2026-09-12). Row 41 anticipated Google renaming tags again (`google_apis` → `google_apis_ps16k`); what happened instead is that `platforms;android-37.2` was promoted to **channel-0** while BOTH of its system images stayed on **channel-2** (dev) [Verified against Google's live `sys-img2-3.xml` files]. `android sdk install` is stable-only and **exits 0** on `Package not found`, so both images were silently skipped and the verify loop in `global-stack-android-setup.sh` FATALed — loud at the end, silent at the install. Note the 37.2-**beta** images ARE channel-0, which is exactly why the previous `37.2-beta1` pin worked and the promotion broke it. The three `platforms` records now carry `(require-sibling:URL|ID_TEMPLATE,…)`, which keeps only levels whose every listed system image is present, channel-0 and not obsolete in the named sys-img XML, filtered BEFORE channel selection so `(offset:N)` counts qualifying levels only. Each pair carries its own URL because the tag → document mapping is data Google publishes, not a rule derivable from the id. It fails CLOSED: an unreachable companion XML is `ERROR`, never an empty filter that would pass every candidate exactly when the check could not run. **The window therefore means "the three latest FULLY INSTALLABLE levels"** and can trail Google's platform releases by weeks, advancing on its own once the images are promoted. **The correction direction is DOWNWARD, so `decide.sh` rule 5 makes it a `SKIP`** — `--apply` will never walk the window back; the three values are hand-edited and the gate's job is to stop the next `--apply` re-picking the broken level. `env-update.test.sh` §124 pins all fourteen properties. Adding a slot means: `.env` (annotation + var), the four compose files including the gitignored `local.05` one, `_pkgs` in setup.sh, the one-line `GS_ANDROID_SDK_WANT`, and §27/§47's 14-input pins — §47 checks setup.sh against the composite both ways, so a slot added on one side reds on the other.
- **`android`'s `--sdk` is a GLOBAL option — `android --sdk=<path> sdk install …`, never `android sdk install --sdk=…`.** The second form is rejected outright: `Unknown option: '--sdk=…'`, exit **2**, for `sdk install` and `sdk list` alike [Verified 2026-09-11 against `android 1.0.15985488`, the build the pinned `commandlinetools-linux-${GLOBAL_STACK_ANDROID_SDK_BUILD}_latest.zip` yields — so a clean machine reproduces it]. `b2ae4d1` shipped the wrong position at all three call sites in `global-stack-android-setup.sh` and nothing noticed for a day, because `gs_version_gate` returns `skip` on a warm `tools/` volume (`make down` does not clear `versions/`; `make hard-restart` REPLACES `tools/` with `var/tools` — `sudo rm -rf tools` then `cp -R var/tools/ tools` — so it is warm only when `var/tools` is a full snapshot, and on 2026-09-28 it was a 244K skeleton with no `versions/`, i.e. a full cold install [Verified: read the `hard-restart` recipe and `du -sh var/tools`]) — the block had literally never run. It was armed, not harmless: `global-stack-android-start.sh` (its `sudo rm -rf "${ANDROID_HOME}" …` line) `sudo rm -rf`s `ANDROID_HOME` **before** calling setup, so any of `RELOAD_ANDROID=true`, a bump of a pinned SDK var (three of them then; twelve since row 33, fourteen since row 41 — see §47), a missing `android.cli` marker (named `android.sdkmanager` until row 46 — `android-start.sh` moves an old one into place before the gate, so the rename itself never triggers the wipe; `startup-prologue.test.sh` §53), a clean machine or `make soft-restart` would have deleted a working SDK and then failed on the first command of the reinstall. Two more facts worth keeping, both measured: `android sdk list` with no `--all` lists **installed only**, so it is a real verification surface; and its id column is the install id with `;`→`/`, uniformly. **Three packages are SINGLE-INSTANCE upstream — `platform-tools`, `ndk-bundle` and `emulator` — and a single-instance id takes NO version, on BOTH sides: installed bare, listed bare with the version upstream served in column 2.** Send one a `;<ver>` and the CLI prints `Package <id>/<ver> not found.` and **exits 0**, installing nothing [Verified 2026-09-11, all three; multi-instance `build-tools;37.0.0` is accepted in the same run]. Row 31 got only half of this: it fixed the LISTING side with a `"platform-tools;"*) _id="platform-tools"` exception while `_pkgs` still sent `platform-tools;${…_VERSION}` — so the package could never install. **The shipped verify CAUGHT it; the SUITE did not.** On the first boot that ever ran this block it printed `FATAL: android sdk install reported success but these packages are absent: platform-tools` and exited 1 [Verified 2026-09-11 18:36, live `04android` log] — the exception's listing-side half was correct in itself, so it mapped the dead id to bare, grepped the real listing, found nothing, and failed exactly as designed. What stayed green was §43: its stub recorded whatever id it was handed and then re-applied the script's own `;`→bare transform when listing, so *in the suite* a package that could never install reported itself present — *a stub that mirrors the code's assumption tests nothing but the mirror*. Scope the `adb` outage honestly: the measured absence window is that one failed reinstall (18:36 → the fix), because before it the block had never run (warm-volume `skip`) and the pre-row-31 install's `platform-tools` was still on disk — [Unverified beyond that: `android-start.sh` (its `sudo rm -rf "${ANDROID_HOME}" …` line) `sudo rm -rf`'s `ANDROID_HOME` before calling setup, so the pre-18:36 tree can no longer be inspected]. Fixed row 38: bare on both sides, the exception deleted, and the `.env` pin reinterpreted as an **expected** version (it is not requestable) asserted against the installed build with a **WARN**, since the only remedy for real drift is an `.env` bump. `startup-prologue.test.sh` §43g/§43g2 pin the `--sdk` position, §43p–43t run the shipped block against a stub that now rejects a version suffix on all three ids, §43z is the static class guard so an `ndk-bundle;<ver>` regression reds too, and §43aa–43ac cover the version assertion.
