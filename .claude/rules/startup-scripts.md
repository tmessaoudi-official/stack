# Container startup scripts — knowledge for editing them

Split out of `CLAUDE.md` by `/rules-split` on 2026-10-09: the text below is unchanged except for cross-references and line citations, and each entry keeps a one-line index entry in `CLAUDE.md`. A new lesson about these files belongs HERE, not in `CLAUDE.md`.

## From CLAUDE.md § Testing & Verification

- **Shared prologue**: `docker/config/dist/bin/base-bin/global-stack-base-prologue.sh` — defines `stackCatch` + `trap` for all startup scripts (51 scripts source it — 02sonarqube joined 2026-09-28). Excluded: caddy/httpd/nginx server scripts, android-setup, localstack, selenium-chrome/firefox and utility helper scripts (deliberate **141**-exempt variant — they keep their own `stackCatch`). `04serverless-framework` used to be excluded too, but it kept no handler of its own, so its exemption silently meant "no error reporting at all" for a service that advertises an error token and a marker healthcheck; it now sources the prologue like everything else. The old **141/1** exemption is gone: exit code 1 is the most common real failure in the web servers' own chain (their `*-setup.sh`, `*-iou-common.sh` and `*-iou.sh` all end their error path in `exit 1`). Gone from **all 11** handlers only since 2026-09-04: the 2026-08-29 migration reached 8, and `caddy-iou.sh`, `httpd-iou.sh` and `nginx-iou.sh` kept the exemption until row 25, because `startup-prologue.test.sh` §19 iterated a hardcoded list that omitted exactly those three. §19 now discovers handlers instead, and exempting it produced total silence rather than a tolerated error. Dropping it changes no control flow — `set -e` already aborts wherever the ERR trap fires — but it does require the `_STACK_CAUGHT` re-entry guard those handlers now carry, because the `-ne 1` arm had been serving that role by accident. **The exempt family is 14, not 11** (row 30, 2026-09-11): the three `android-bin` handlers are members too, and row 25's sweep was scoped by its own Files cell to the three web-server trees, so they kept the exit-1 exemption — and §19's *discovery roots* were still hardcoded to those same three directories, the identical can-never-fire defect one level up. `android-start.sh` was the worst of the three: it alone lacked the 141 exemption and wrote **no error token at all**, so any failure left it alive in `sleep infinity` (deliberate — the container stays reachable for `make login-04android`) with nothing in `tools/errors/`, i.e. unhealthy and unattributable for the full 24h `start_period`. All three now carry the guard, the 141 exemption, a token write, and the canonical `** command:` elapsed field; `.claude/skills/new-service/SKILL.md` scaffolded the same pre-row-25 shape and was fixed with them.

## From CLAUDE.md § Gotchas & Pitfalls

- **Downloaded tools refuse a release they cannot check** (tranche 2 step 15, tranche 3 steps 22/24). symfony-cli, fabpot and caddy's xcaddy must publish a `checksums.txt` that lists the linux asset, or the pin FATALs at boot and the old copy stays. nginx's tarball must carry a good signature by one of the five nginx.org keys committed in `nginx-bin/nginx-release-keys.asc`, whose primary fingerprints are pinned in `global-stack-nginx-iou.sh`: a release signed by a new key FATALs 01nginx until both files are updated (fail-closed by design; the `sb` key expired in 2016, `thresh` expires in 2027); `env-update`'s `github:` fetcher cannot pre-check that (`(verify-asset:)` is `url`-only), so confirm it before applying such a bump. elasticmq (row 28) and fvm (row 29) are checked against the SHA-256 GitHub serves as the release asset's `digest`: a release without one is refused at boot (old copy kept), and each check makes an unauthenticated `api.github.com` call (60 an hour per IP, shared by both and by env-update's `github:` fetcher), so a bump applied right after a large `--check` can FATAL on the rate limit alone — restart once the hour has passed. zephir, phalcon and pickle cannot run under 02phpbrew's system php (no mbstring), so their VERSION is pinned by the release URL plus the Phar signature only — UNCERTIFIED-BY-EXECUTION.
- **phpbrew extracts into `tools/phpbrew/build/tmp.<time()>` — a dir shared by every 03php* container — so two that began extracting in the same second used to destroy each other's source tree** (2026-09-28 cold start; `docs/plans/phpbrew-extract-collision.plan.md`). `03phpedge` and `03php8-5` started 0.4 s apart and both got `tmp.1790632049`; phpedge finished first and its `__destruct` `rm -rf`'d the dir under 8.5.11's tar (`rm: cannot remove '…/php-8.5.11/Zend': Directory not empty` in phpedge's log) [Verified: both logs, `ExtractTask.php:45,51`]. tar recreated only the tail of the archive, leaving `build/php-8.5.11` ~5,700 files short of its tarball, and phpbrew then reused it on every retry because its "already extracted" test is only `file_exists(<dir>/configure)` and `configure` sorts late in the archive [Verified: `ExtractTask.php:36-38`, the `skipping...` line in 5 of 6 attempts]. What you SEE is unrelated to the cause: `tools/errors/php.8.5`, exit 255, and a compile error about a file that is in the tarball (`dtrace … zend_dtrace.d: No such file`), repeated identically until `on-failure:5` is spent, with five dependents left in `Created`. Only a COLD start can hit it. Fixed at the origin by the overlay `ExtractTask.php` (`tmp.<time()>.<random hex>` — **not** a PID suffix: every container has its own PID namespace and boots identically, so siblings share low PIDs). **The overlay reaches `phpbrew-src` only through `phpbrew-iou.sh`'s FRESH clone** (cold start, `RELOAD_PHPBREW`); a clone made before an override existed never gets it — re-apply with `rsync -a docker/config/dist/conf/phpbrew/source/src/ tools/phpbrew-src/src/`. Recovering a tree damaged this way: `rm -rf tools/phpbrew/build/php-X.Y.Z tools/phpbrew/php/php-X.Y.Z` (keep `distfiles/`), then start the container through `env -i HOME=$HOME PATH=$PATH make up`; the setup-mode start clears its own error token. To diagnose, diff `tar -tjf distfiles/php-X.tar.bz2` against `rtk proxy find` of the tree **under `LC_ALL=C`** (`sort`/`comm` here skip `_` and report "not in sorted order" otherwise) and never count with an rtk-rewritten `ls` (it reported 51 for a 498-entry directory); the ~19 `ext/*/tests` names that always differ are non-ASCII filenames `tar -t` octal-escapes. **UNCERTIFIED-BY-EXECUTION: the concurrent race itself** — proven by the unit test plus one uncontended extraction, not by a cold start with two installs beginning in the same second
- **Four images BAKE their start script — an edit needs an image rebuild, not a restart.** Every other service that runs one of our start scripts goes through `global-stack-base-sync-bin-n-exec.sh`, which copies the bind-mounted `docker/config/dist/bin` into `/usr/local/bin` first, so a script edit applies on the next restart. `01localstack-localstack`, `01selenium-standalone-chrome`, `01selenium-standalone-firefox` and `02sonarqube` instead `COPY` their `*-bin/` (and `base-bin/`) into `/usr/local/bin` at BUILD time and `CMD`/`ENTRYPOINT` straight into it, so the bind-mounted copy is never run [Verified 2026-09-28: after the step-2 edit, a recreated 02sonarqube still ran the old script — md5 of `/usr/local/bin/global-stack-start-sonarqube.sh` differed from the bind mount, and java was PID 1's direct child]. After editing one of them: `env -i HOME=$HOME PATH=$PATH make GLOBAL_STACK_DOCKER_CLI_EXEC=build GLOBAL_STACK_DOCKER_CLI_SERVICE=<svc> GLOBAL_STACK_DOCKER_CLI='docker compose' GLOBAL_STACK_DOCKER_CLI_FLAGS='--env-file .env.local' docker-cli`, then recreate that service. The same holds for the shared `base-bin/` helpers those four copied (the prologue included)
- **`tools/versions/` markers** control reinstall — all are **content-compared** by the `gs_version_gate` helper (defined in `base-bin/global-stack-base-version-gate.sh` since 2026-09-04; the prologue SOURCES it, and the prologue-exempt scripts source the helper alone): when a marker's content differs from the current env version, reinstall triggers automatically **with a loud WARN** (no manual marker deletion needed). **What the marker holds is the manager-RESOLVED version, not the raw pin** — `pyenv`/`rbenv`/`nvm` all write `find-latest`/`nvm version` output — so anything comparing against it must resolve first. pyenv and rbenv do (since 2026-09-02, and they reuse that one resolved value at the install site so the two cannot drift). **nvm still gates on the raw pin**: its resolver is `nvm version`, which needs nvm sourced ~130 lines further down. It is latent only while every node pin is fully qualified; a partial pin like `v24` would recompile on every boot. Do not copy the pyenv shape into nvm without moving the source first. Coverage is now UNIVERSAL for runtime-installed tools (Track 5, 2026-09-04): managers, tier-03 per-version markers (`node.24`, `php.8.4`, …), per-package slot markers (`<rt>.<AS>.pkg.<slot>`), and every runtime install site — nvm deno/bun, the 11 phpbrew tools, the 5 rust tools, the android SDK components, phpmyadmin, elasticmq, the rbenv plugins, the 00base tools (go/zig/hurl/mise) and all 17 web-server compare sites. **The gate now lives in its own sourceable helper**, `base-bin/global-stack-base-version-gate.sh`: the prologue sources it, and the prologue-EXEMPT scripts (caddy/httpd/nginx, android) source the helper ALONE so they reach the gate without taking the prologue's error handling. Two sites are deliberately NOT gated and must stay that way: `frankenphp`, whose artifact path embeds its version so a bump already fetches a different file, and `awscli`, which has no `.env` pin at all. The marker is always written LAST in an install branch, so under `set -e` a failed install cannot leave a satisfied marker behind. Deleting a marker still forces reinstall, and `GLOBAL_STACK_RELOAD_*=true` forces one (see the `RELOAD_*` bullet in CLAUDE.md § Gotchas for the three that do not wipe). Note: `make down` clears `successes/`+`errors/`+`locks/` but NOT `versions/`, so these markers persist across restarts as designed. `php.edge` (branch `next`) is now SHA-tracked: its `@todo env-update` annotation uses `(use-sha) (version-prefix:github.com/php/php-src@) github:php/php-src`, so `env-update` resolves php-src HEAD → `GLOBAL_STACK_PHPEDGE_VERSION=github.com/php/php-src@<sha>` (phpbrew builds that commit `as php-master`). Because the main `php.edge` marker is the invariant install dirname (`php-master`), drift is detected via a SIDECAR marker `tools/versions/php.edge.build` (holds the resolved build ref); on a SHA change the edge gate WARNs, cleans the `php-master` dirs + markers, and rebuilds. Manual `RELOAD` is no longer required for edge upstream drift
- **`$HOME` in every container is re-permissioned on EVERY boot, and a numeric `chmod` there disarms cached executables.** `base-bin/global-stack-base-chown-home.sh` is called from `00base/conf/bin/global-stack-base-sync-bin-n-exec.sh:9` — the entrypoint of every container — and its file arm used to be `chmod 600`, which also removes the OWNER's execute bit. Any tool that caches an executable under `$HOME` is therefore disarmed on the *next* boot. Two confirmed instances, both found the same day [2026-09-11]: the `android` launcher downloads the real 87 MB CLI to `~/.android/bin/android-cli` at 0755 and execs it — one restart later it is `-rw-------` and the SDK reinstall dies with `Failed to exec android binary: Permission denied (os error 13)`; and serverless v4 caches `sf-core.js`, a bundled `esbuild` and `invoke.py` under `~/.serverless/releases/<ver>/` at 0755. **Which of those actually needs the bit is a measurement, not a reading — an earlier draft of this bullet blamed `binary.js`'s `existsSync(binaryPath)` gate and was wrong**: `binaryPath` resolves to `<serverless>/node_modules/.bin/serverless-linux-amd64-<v>`, under `tools/`, which `chown-home` never touches [Verified: read `binary.js:172-182`, then `ls -l` the resolved path — 0755, outside `$HOME`]. Measured with all three release files at 0600, `serverless --version` still returns `4.42.0` unchanged, because the Go launcher runs `sf-core.js` through `node` and read access suffices; but the bundled `esbuild` is a native ELF that answers `Permission denied` at 0600 where 0755 prints `0.28.2`, so a bundling or deploy path that shells out to it breaks [Inferred — no deploy was run]. **It is ARMED, not always-firing**, which is why it hid for so long and why uptime proves nothing here: a normal boot never invokes `android` (`gs_version_gate` returns `skip`, and `avdmanager` is a 5760-byte shell script calling `java` directly, with zero references to the cached CLI), so only a *reinstall* boot — an `.env` bump of any of the 12 pinned SDK inputs, `RELOAD_ANDROID=true`, `make soft-restart` — meets a cache the previous boot already stripped. Same hiding pattern as the `--sdk` bug (`.claude/rules/android.md`). Fixed row 39 with `chmod ug-s,go-rwx`: every group/other bit gone, setuid/setgid gone, the owner's bits untouched — it can only PRESERVE an `x` that was already there, never add one, so nothing non-executable today becomes executable. ssh is the constraint that motivated `600` and it is satisfied: OpenSSH rejects a private key only on a group/other bit (`mode & 077`), so 0700 is accepted exactly like 0600 [Verified against a real `sshd`: 600 and 700 accepted, 640/660/604 rejected `UNPROTECTED PRIVATE KEY FILE`]. The `ug-s` clause is not belt-and-braces — `chmod 600` cleared setuid unconditionally, and while the preceding `chown -R` happens to clear it too, relying on that makes an unconditional guarantee depend on statement order. The `.docker/cli-plugins` `a+x` arm was **deleted, not joined by a second special case**: it never fired (no container has that directory; docker's plugins live in `/usr/libexec/docker/cli-plugins`), and under the new rule a plugin arriving at 0755 keeps owner-execute with no exception needed. `startup-prologue.test.sh` §51 pins all of it.
- **A trailing `[[ cond ]] && cmd` makes the FALSE test the script's own exit status.** bash returns the last command's status, and a short-circuited AND-OR list whose left side failed returns 1 — so a script whose last statement is a *guarded* action reports failure for having had nothing to do [measured: var unset → 1, set → 0]. Four scripts carried it (row 32, 2026-09-11). In `android-bin/global-stack-android-setup.sh` it is unreachable today **only because `global-stack-android-start.sh` exports `GS_ANDROID_SDK_WANT` before its single call site** (line 115 [as of 2026-09-11] — the export is the anchor, not the number) — an accident of the caller, not a property of the script. In `node24/node26/nodeedge-bin/global-stack-nvm-*-setup.sh` it IS reachable: those files' entire working body is two lines and everything below is commented out, so the guarded `\. "${NVM_DIR}/bash_completion"` is the last statement, and `nvm-bin/global-stack-nvm-start.sh` calls each as a bare statement inside its `[[ ! -f versions/node.<label> ]]` install branch (line 143 [as of 2026-09-11]) under `set -xeEu` with the prologue's ERR trap — a missing completion file would abort the node install and write an error token. The fix is an `if`, **never** a trailing `|| true`, which would be the bandaid. `startup-prologue.test.sh` §46 DISCOVERS the class rather than listing it (a hardcoded list of four would be §19's defect again) and is deliberately narrowed to a **test-led** `&&`: `phpbrew update --old || true`, `dig +short "${1}" || echo ""` and any real command's `&&` are legitimate last lines, present in this tree, and must stay green. Known hole, measured not assumed: a backslash-continued `[[ cond ]] && \` puts the `&&` on the penultimate line and is not caught; no script uses that shape today.
