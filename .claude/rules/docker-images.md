## From CLAUDE.md § Testing & Verification

- **Postgres healthcheck tests**: `bash bin/tests/postgres-healthcheck.test.sh` — 7 checks, ~5 s, needs docker and the built `global_stack-01postgres18` image (aborts rather than passing vacuously without them). §1 reads the resolved compose config (clean env, only the keys under test): a TCP `pg_isready -h`, the patient window (24h / 99999) and `PGCTLTIMEOUT >= 300`. §2 runs the SHIPPED check, extracted from the healthcheck, inside a throwaway container on an anonymous volume — never the stack's volume — during the entrypoint's socket-only init server (must FAIL: this is the 2026-09-28 false positive that let 02sonarqube start too early) and after it (must pass), and asserts `PGCTLTIMEOUT` reaches the postgres-user process that runs `pg_ctl -w stop`. It does not prove 300 s is enough under load; only a fresh-volume bring-up does
- **mongo9 rseq tests**: `bash bin/tests/mongo9-rseq.test.sh` — 4 checks (+1 with `GS_MONGO9_PROBE=1`, which starts a throwaway `mongod` from the built image; no stack volume, no port). Pins that `docker/images/01mongo9` resets `GLIBC_TUNABLES` and that nothing (compose included) sets it back. Check 3a reads the BUILT image, so it reds until `01mongo9` is rebuilt (the build command is in the "Four images BAKE" gotcha, `.claude/rules/startup-scripts.md` — 01mongo9 builds the same way). Comment lines are stripped first. Three sabotages each red their own check
- **Compose env plumbing tests**: `bash bin/tests/compose-env-plumbing.test.sh` — 27 checks that a var the containers read at RUNTIME actually reaches them. §8 (2026-09-28) derives every java consumer (a service with `JAVA_VERSION` and `SDKMAN_INSTALL_PACKAGE_*` slots that is not `03java*`) and the `03java*` provider sharing its `JAVA_VERSION`, and reds on any `sdk use` package the provider never installs — the Java 27 consumers took groovy VX2 + spark 3.5.8 from the Java 17/21 set, so 04android started only if 03java17/21 happened to finish first. It resolves THROUGH MAKE (see the `make up` gotcha, CLAUDE.md § Gotchas), with a `>= 3` consumer / `>= 30` pair floor. §7 (pin-audit step 26) covers the pins 00base installs at boot: go/zig/mise (and the bare `MISE_VERSION` that install-mise exports to the host) were build args only, frozen in the image ENV, so a bump plus a restart installed nothing; the pin set is derived from the installers `base-start.sh` calls, and hurl is exempt by name and asserted to stay OUT of the runtime env (the image compiles it, so its pin must come from the same build). It resolves the config once, keeps only the key under test (never the expanded `env_file` values), derives the reader set from `git grep` over the startup scripts rather than a list in the test, and asserts the resolved value *tracks* `.env.local` — a hardcoded literal in the fragment would otherwise pass. Aborts rather than passing vacuously when `docker`/`jq`/`.env.local` are missing

## From CLAUDE.md § Gotchas & Pitfalls

- **Two images sit on FOREIGN, EOL bases — never copy the `00base` apt idiom into them.** Every other image here descends from `00base` (`ubuntu:resolute-20260901`), where `apt-get update --allow-releaseinfo-change` is valid. Exactly two do not: `01epiclabs-docker-oracle-xe-11g` is **Ubuntu 16.04 xenial, apt 1.2.32** and `02mongoclient-mongoclient` is **Debian 8 jessie, apt 1.0.9.8.6** [Verified 2026-09-11 by reading `etc/lsb-release` + `var/lib/dpkg/status` out of each image's layer 0]. Both predate that option — it landed in the **apt 1.5** cycle, 2017 [Verified 2026-09-11 against apt's own `debian/changelog`: the behaviour entries sit under `apt (1.5~alpha1)` and the flag is named verbatim in the `apt (1.5~rc2)` typo fix; an earlier draft of this bullet said 1.9.3 from recall, which is wrong] — and reject it with `E: Command line option --allow-releaseinfo-change is not understood in combination with the other options`, **exit 100** — which is exactly how `1aa924f` broke the build: it copied the `00base` idiom into both. The two need *different* cures and must not be treated as one class. **epiclabs**: xenial is still served on archive.ubuntu.com (HTTP 200; `old-releases` 404s), so dropping the flag is the whole fix. **mongoclient**: jessie is archived, so `deb.debian.org` 404s and `apt-get update` exits 100 *even without the flag* — and worse, the image was slimmed by deleting `/usr/share/zoneinfo` **without telling dpkg**, which still reports `tzdata 2019c` as `install ok installed` owning 1902 files, so `apt-get install tzdata` is a **silent no-op** (success, nothing installed) and `--reinstall` cannot download. Its zone files therefore come from a pinned `ubuntu:${GLOBAL_STACK_IMAGE_UBUNTU_VERSION}` build stage via `COPY --from` (jessie's glibc 2.19 reads modern TZif fine — CEST/CET verified). Note the shape of the trap: **a green build proves nothing here** — with the `COPY` removed the build still exits 0 while `date +%Z` prints the literal `Europe`, so the guarantee is only provable by running the container [Verified: sabotage, 2026-09-11]. Read `startup-prologue.test.sh` §35c/§35e for what they are: **text guards that PIN the mechanism, not a runtime test of the timezone**. They red if someone deletes the `COPY` or re-adds the flag, and that is their whole job; nothing in any suite runs either container, so "618 tests pass" is not evidence that `date +%Z` is right. The certification for that is manual and was run by hand at row 40 — as each image's OWN default user (`root` for epiclabs, `node` for mongoclient), because a `--user root` probe would not prove mongoclient's real user can read the copied tree: `docker run --rm -e TZ=Europe/Paris --entrypoint sh <image> -c 'date +%Z; TZ=Europe/Paris date -d 2026-01-15 +%Z'` → `CEST` then `CET`. **The `-e TZ=` is not optional in that command** — neither Dockerfile sets `ENV TZ`, the compose file supplies it, so without it the first field prints `UTC` and reads as a regression that is not there [Verified 2026-09-11: verbatim without `-e`, both images print `UTC CET`; with it, `CEST CET`]. Note the probe replaces the entrypoint, so it proves glibc resolves the zone, NOT that the service's own process picks it up. For Oracle, `/usr/sbin/startup.sh` IS the entrypoint and contains **no** `TZ` reference at all [Verified 2026-09-11: `grep -nE '\bTZ\b|TIMEZONE' /usr/sbin/startup.sh` → rc 1], so the Oracle processes inherit `TZ` from the container environment rather than any script reading it — and whether they then resolve the zone the way glibc-in-`sh` did has never been observed.
- **`{ [ toggle ] && installer || echo "… will not be installed"; }` in a Dockerfile runs the echo when the installer FAILS** — not only when the toggle is off. Under the `SHELL -e` of the RUN, that turned four real install failures into a green `00base` build on 2026-09-28: difftastic 0.71.0's renamed asset 404'd (`curl -L` without `-f` saved the error page, `tar` exited 2) and killed install-tools before sonar-scanner-cli, bat, sops, rtk, claude and yq; and gitlab-runner had been failing on its own (`rm` of a `.sources` file GitLab no longer writes, then a `cp` into a never-created `~/.gitlab-runner`); Docker-in-Docker died at `groupadd docker` (exit 9, docker-ce already made it) before its compose/buildx plugins; and `rtk init --global` ran as root into a missing `/root/.claude`. The damage surfaced two images later as `02sonarqube`'s `COPY --from=… /opt/developer/sonar-scanner-cli: not found`. All 15 such lines are now `if …; then …; else …; fi`, and `bin/tests/base-install-tools.test.sh` §4 reds on a new one. When an image lacks a tool its toggle enables, suspect the installer before the COPY that reports it.
- **`mongo:9.0.x` refuses to start on kernel >= 6.19 BECAUSE of its own `ENV GLIBC_TUNABLES glibc.pthread.rseq=0`** (SERVER-121912; measured 2026-10-01, kernel 7.0.0-34, `global_stack-01mongo9`). With the image default the container exits with `MongoDB cannot start: Linux kernel versions 6.19 and newer has a known incompatibility`; with the tunable cleared it ran the real entrypoint, took 200k inserts and survived a restart. `docker/images/01mongo9/Dockerfile` therefore sets `ENV GLIBC_TUNABLES=""` (the image bakes it — an edit needs a rebuild, a restart is not enough). **This is a trade-off, not a free fix, and it is undocumented:** the 6.19 guard lets mongod through when glibc keeps rseq, while mongod's older startup text still advises the opposite [Inferred: that pattern suggests the guard tolerates the no-per-CPU path, not that MongoDB endorses it]. The binary says *"Your system has glibc support for rseq built in, which is not yet supported by tcmalloc-google and has critical performance implications. Please set GLIBC_TUNABLES=glibc.pthread.rseq=0"* — i.e. upstream recommends the very value that now trips the 6.19 guard. Cleared, tcmalloc runs WITHOUT per-CPU caches (`db.serverStatus().tcmalloc.usingPerCPUCaches` → `false`, measured) and mongod logs that warning at startup: slower allocation and more memory, acceptable for local dev, wrong for production. [Inferred: tcmalloc registering its own rseq under `rseq=0` is what breaks on 6.19 — the mongod binary carries `__rseq_cs_TcmallocSlab_*` symbols, but the guard's exact condition was not read from source.] It is a property of the `mongod` binary, not of the Ubuntu base: MongoDB publishes NO `mongodb-org-server` for resolute (only `mongodb-database-tools`), so rebasing onto the stack's resolute image is unsupported and would not help. The ticket is closed "Gone away" with no fixVersion, so **re-probe on every MONGO9 bump** (`GS_MONGO9_PROBE=1 bash bin/tests/mongo9-rseq.test.sh`) — a release that fixes tcmalloc makes this override obsolete. The 7.0 → 9.0 data jump is not a risk here: the existing `01mongo9_data` volume was inspected read-only and is empty (4.0K, no files) [Verified 2026-10-01]. The developer reported the real `make up` bring-up working on 2026-10-01 (his word, after c1ca3ed; not re-run by Claude). Still UNCERTIFIED-BY-EXECUTION: `02mongoclient` 4.0.1 (an old driver) talking to mongod 9.0 was not separately confirmed.
- **Postgres reports `en_US.utf8` collation but SORTS AS C, and the existing volume still does.** The image is `18.x-alpine` (musl): `localedef` is absent and `/usr/lib/locale` is empty, so glibc locales cannot exist there — yet the image ships `LANG=en_US.utf8`, so `initdb` recorded `datcollate=en_US.utf8` under the libc provider and silently degraded to C. Verified on the running cluster: `ORDER BY` returns `Banana,Zebra,apple,cherry` (code-point order) while `pg_database` claims `en_US.utf8` [2026-09-10]. Two consequences. **(1)** Sort order differs from any glibc production, so `ORDER BY name` can disagree between dev and prod with nothing in either config hinting at it. **(2)** If the effective collation ever changes — a Debian-based image, locales appearing in a rebuild — every existing text index is silently wrong until `REINDEX`; that applies to real data here (`keycloak` plus six `*_grdf_clts` databases). `01postgres18`'s compose now sets `POSTGRES_INITDB_ARGS=--locale-provider=builtin --builtin-locale=C.UTF-8` and `LANG=C.UTF-8`, which yields `datcollate=C, provider=b, locale=C.UTF-8` with **identical** sort order — honest labelling, no behaviour change. But `initdb` only runs on an EMPTY data dir, so **the existing volume keeps the lying metadata until it is recreated** (`make hard-restart`, or dropping `*_01postgres18_var_lib_postgresql`). Do not add `--lc-collate`/`--lc-ctype`: `initdb` rejects them alongside the builtin provider and the container fails to start. ICU is available in the image (908 collations) if real locale-aware ordering is ever wanted — that needs a re-init and a dump/restore.
